This document describes how Common Ground is deployed: the four deployment
targets, the single-server self-host stack in detail, how instance identity is
injected at serve time, how optional third-party integrations degrade, and the
legacy CI/CD pipelines. It complements
[`docs/infrastructure/`](../infrastructure/) (which documents the dev Docker
Compose stack, the Caddy edge and build process) and the operator-facing
[`docker/SELFHOST.md`](../../docker/SELFHOST.md).

---

## 1. Deployment matrix

Common Ground runs from a single codebase in four configurations. The
`DEPLOYMENT` mode (`prod` / `staging` / `dev`) drives feature flags, the default
chain set and various semantics; it is decoupled from the domain (see §2).

| Target | Compose file / driver | Domain(s) | `DEPLOYMENT` | TLS | Secrets | Media/RPC |
|---|---|---|---|---|---|---|
| **Dev** (local) | `docker/docker-compose.yml` via `./run.sh` | `localhost` | `dev` | Caddy's local CA (`tls internal`) / plain HTTP on :8000 | `docker/.env` (gitignored), generated from `docker/.env.example` with random secrets on first `./run.sh` | hardhat dev chain, test contracts |
| **Staging** | Azure DevOps → Docker Swarm (Ansible) | `staging.app.cg`, `id.staging.app.cg` | `prod` build, staging registry | edge (Cloudflare) | CI secrets / infra repo | live chains (`eth,xdai,lukso`) |
| **Prod app.cg** | Azure DevOps build → manual Swarm deploy | `app.cg`, `id.app.cg` | `prod` | edge (Cloudflare) | infra repo | live chains |
| **Self-host** | `docker/docker-compose.selfhost.yml` via `docker/selfhost/selfhost.sh` | operator's own domain | `prod` on any domain | Caddy + Let's Encrypt (in-stack); Caddy's local CA for test instances (`CG_TLS_MODE=internal`) | generated by `init.sh` into `.env.selfhost` | free public RPCs by default; no dev chain |

Key differences of the self-host profile vs. the dev/CI stacks (from the header
of `docker-compose.selfhost.yml`):

- Caddy (`docker/caddy/`, `Caddyfile.selfhost`) is the edge: TLS for the app
  and mediasoup call signalling — Let's Encrypt by default, or Caddy's own
  local CA with `CG_TLS_MODE=internal` (LAN/test instances) — plus the
  frontend, the routing, the security headers and the instance config; no
  external CDN required. Call signalling on `:4443` is added by
  `docker-compose.selfhost.calls.yml` only when calls are enabled.
- `DEPLOYMENT=prod` gives full production semantics on any domain.
- No hardhat dev chain, no test contracts.
- Postgres loads the tuned `docker/db/postgresql.conf`.
- Valkey (Redis-compatible) memory is tuned for a small single machine:
  `REDIS_MAXMEMORY` (state instance) and `REDIS_CACHE_MAXMEMORY` (cache).
- The compose project is named `cg-selfhost`, so its containers and volumes
  stay separate from the dev stack even in the same directory.

## 2. Instance identity and config injection

Historically the frontend decided its mode by matching the browser URL against
hardcoded domains (`app.cg` → prod, `staging.app.cg` → staging, anything else →
dev). Self-hosted instances would silently run in dev mode. Instances now
**declare who they are at serve time**: both HTML shells load
`/instance-config.js`, which sets a global:

```js
window.__CG_INSTANCE__ = {"deployment":"prod","appUrl":"https://chat.example.org", ...};
```

The same build artifacts therefore work on any domain — the domain is
configuration, not code.

### Producers of the config

| Path | File | Used for |
|---|---|---|
| Caddy edge (per request) | `docker/caddy/instance-config.js`, a Go template rendered by Caddy's `templates` handler at `/instance-config.js` | every page of the web app: the static shells and the share-link pages the API renders (they carry the same `<script defer src="/instance-config.js">` tag) |
| Backend (runtime) | `srv/util/instanceConfig.ts` — `buildInstanceConfig()` | `GET /api/v2/Instance/config` (native clients, bots, the SDK); `instanceConfigScriptTag()` only for a shell without the script tag |

The template is driven by `CG_*` env passed to the `caddy` container in
`docker-compose.selfhost.yml` (`CG_APP_URL`, `CG_DEPLOYMENT`, `CG_LEGACY_CGID`,
`CG_PASSKEY_RP_ID` (= `PASSKEY_RP_ID`, empty = the `CG_DOMAIN` host), `CG_CGID_URL` (emitted only
with `CG_LEGACY_CGID=true`; derived from `CG_ID_DOMAIN`),
`CG_RECAPTCHA_SITE_KEY`, `CG_CAPTCHA_PROVIDER`, `CG_ACTIVE_CHAINS`, the `CG_FEATURE_*` capability
booleans, `CG_ENABLE_CALLS`, `CG_ENABLE_IMAGE_FILTER`, `CG_IMAGE_FILTER_THRESHOLD`, `CG_GIPHY_API_KEY`,
`CG_WALLETCONNECT_PROJECT_ID`). The object is encoded by Go's JSON encoder,
never pasted into script text. Without `CG_APP_URL` (the dev stack) the
script declares nothing and the frontend falls back to its built-in
detection. The two producers implement the same rules separately — keep them
in sync.

### Config shape

Defined and validated in `src/common/instance.ts` (`InstanceConfig`). Fields:

| Field | Meaning |
|---|---|
| `deployment` | `prod` / `staging` / `dev` — semantic mode |
| `appUrl` | public base URL, no trailing slash |
| `cgidUrl` | legacy CG ID (gateway) instances only: CG ID app base URL including the hash-router prefix (`.../#`) |
| `passkeyRpId` | WebAuthn RP ID of the passkeys on this origin (`PASSKEY_RP_ID` / `CG_PASSKEY_RP_ID`, default the app host); absent on a legacy CG ID instance |
| `recaptchaSiteKey` | reCAPTCHA v2 site key (empty disables the default key) |
| `captchaProvider` | active captcha provider (`altcha` / `recaptcha` / `off`) |
| `activeChains` | chain keys this instance offers (subset of `AVAILABLE_CHAINS`) |
| `features` | capability flags `{ email, twitterAuth, calls, imageFilter, passkeys }` — `passkeys` is false only on a legacy CG ID instance; `email` from a valid SMTP configuration (`SMTP_HOST` set), `twitterAuth` from configured secrets, `calls` from whether the mediasoup service is deployed, `imageFilter` from whether the server-side NSFW filter is enabled (gates the client pre-upload warning) |
| `imageFilterThreshold` | this instance's `IMAGE_MODERATION_THRESHOLD` (0 < t ≤ 1, default `0.8`), so the browser pre-check warns at the confidence the server actually rejects at; ignored when `features.imageFilter` is false |
| `giphyApiKey` | Giphy key (empty hides the GIF picker) |
| `walletConnectProjectId` | WalletConnect Cloud project id |

### Consumer and fallback

`getInstanceConfig()` in `src/common/instance.ts` reads and revalidates the
global (type/shape/regex checks per field), caching the result. `src/common/
config.ts` resolves `DEPLOYMENT` in this order:

1. `window.__CG_INSTANCE__.deployment`, if present (self-host);
2. else browser URL match (`https://app.cg` → prod, `https://staging.app.cg` →
   staging, otherwise dev);
3. else the Node `DEPLOYMENT` env var (backend);
4. if none found, it defaults to `prod` "to be safe".

`activeChains` is resolved the same way: instance config in the browser,
`CG_ACTIVE_CHAINS` (comma-separated) on the backend; unknown chain keys are
ignored. The backend forwards its resolved chain list into the instance config
so the frontend agrees with the server. Capability `features` are derived from
which secrets the server actually has configured, so the frontend hides
features that would only fail (an absent flag means "available" — the case for
the official app.cg instance).

## 3. Single-server self-host stack

The full stack runs on **one server** (the operator guide,
[`docker/SELFHOST.md`](../../docker/SELFHOST.md), states a machine with 4–8
cores and 16 GB RAM is sufficient and that the stack idles well under 2 GB, with
RAM mostly consumed under load). One DNS record is required: the app domain
(`CG_DOMAIN`). Passkeys are bound to the app host
([docs/auth-identity §7](../auth-identity/README.md#7-passkeys)); a separate
CG ID origin (`CG_ID_DOMAIN`) only matters for a legacy CG ID (gateway)
instance: `.env.selfhost` carries `PASSKEY_RP_ID=` (empty = the `CG_DOMAIN`
host), `CG_LEGACY_CGID=false` and an empty `CG_ID_DOMAIN`; every backend
service gets the first two, `CGID_URL` / `CG_CGID_URL` (built from
`CG_ID_DOMAIN`) are passed only to `api` and `caddy`, which read them only in
legacy mode, and Caddy serves the CG ID site only when `selfhost.sh` finds
both `CG_LEGACY_CGID=true` and a `CG_ID_DOMAIN` (see [3.4](#34-tls-caddy)).
Existing `.env.selfhost` files that still carry `CG_ID_DOMAIN=id.<domain>`
from an older `init.sh` keep working; the value is ignored (and `up` says so),
so its DNS record can go.

### 3.1 `docker/selfhost/init.sh` — one-time initialization

`./selfhost/init.sh [--tls-internal] <domain> <acme-email> [id-domain] [public-ip] [public-ipv6]`.
Safe to re-run: existing files are never overwritten. `id-domain` is only for
the legacy CG ID gateway — leave it out, or pass `-` when a public IP follows.
It:

1. Detects the public IPv4 address (via `api.ipify.org`, `curl -4`) if not
   supplied — needed for `MEDIASOUP_ANNOUNCED_IP`. A supplied IP is used
   as-is, so a LAN address works for a local test instance; it must be an
   IPv4 address (mediasoup listens on IPv4 only), anything else is refused.
   The public IPv6 address is detected the same way (`api6.ipify.org`,
   `curl -6`) unless one, or `-` for none, is passed as `public-ipv6` or
   `--tls-internal` is given, and is recorded as `CG_PUBLIC_IPV6` — see
   [3.10](#310-ipv6) for why the stack does not use it yet. `--tls-internal` writes
   `CG_TLS_MODE=internal` (see [3.4](#34-tls-caddy)), accepts `-` (or an empty
   string) for the unused ACME email, and requires the IP argument — detection
   would return the router's WAN address, not the one LAN browsers reach. It
   also starts the instance with email off (`CG_ENABLE_MAIL=false`, empty
   `SMTP_HOST`), so a test instance never delivers mail to the internet.
2. Generates `docker/.env.selfhost` (mode `600`) with fresh random secrets
   (`openssl rand -hex`): the four Postgres passwords (`PG_SU_PASSWORD`,
   `PG_WRITER_PASSWORD`, `PG_READER_PASSWORD`, `PG_MEDIASOUP_PASSWORD`),
   `REDIS_PASSWORD`, `REDIS_SECRET`, `S3_SECRET`, plus `SMTP_PASSWORD` — the
   app's login for the built-in mail relay, which the file switches on
   (`CG_ENABLE_MAIL=true`, `SMTP_HOST=mail`, see [3.9](#39-email-smtp-and-the-mail-relay);
   off with `--tls-internal`) — and `CG_BACKUP_PASSWORD` with the other
   `CG_BACKUP_*` settings (see [3.7](#37-backup-and-restore)).
   It also seeds resource-tuning defaults, bot-account limits, blockchain RPC
   endpoints and empty slots for every optional integration. `BUILDER_UID`/`BUILDER_GID` are the invoking
   user's ids — `0` when run as root, which the builder image accepts (it only
   creates a user/group for ids the `node:26-trixie` base doesn't have).
3. Generates `docker/s3_config/s3.selfhost.json` (creating `s3_config/`, which
   a fresh clone lacks) with an S3 secret matching
   `.env.selfhost` for the SeaweedFS filer, mode `600`, owned by whoever runs
   `init.sh`. The `seaweed` container reads it as root at start and copies it
   for its own user (§3.3), so no ownership change is needed. The script runs
   with `umask 077`: `.env.selfhost` and the other files exist with mode `600`
   from the start, not only after a later `chmod`.
4. Generates a self-signed cert (`docker/selfhost/certs/`) for the internal
   Caddy→mediasoup hop.

The generated `.env.selfhost` is the single source of instance credentials and
configuration and must be kept secret. Blockchain RPC endpoints are pre-filled
with free public JSON-RPC URLs (the `QUIKNODE_*`/`INFURA_LINEA` names are
historical — any URL works), so token gating and balance checks work out of the
box; operators can swap in paid endpoints for heavier use. `CG_ACTIVE_CHAINS`
(default `eth,arbitrum,xdai,base,matic,lukso`) selects which chains the instance
offers, driving both backend chain workers and the UI chain lists.

### 3.2 `docker/selfhost/selfhost.sh` — build and operate

Wraps `docker compose --env-file .env.selfhost -f docker-compose.selfhost.yml`,
plus `-f docker-compose.selfhost.calls.yml` when calls are enabled. It needs
the Compose plugin (`docker compose`, v2 or later) and stops with an
explanation otherwise: the standalone `docker-compose` v1 used to be a
fallback, but it ignores `COMPOSE_PROFILES`, so mediasoup, onchain and the
mail relay would silently not start. It also derives `COMPOSE_PROFILES` from
the optional-service switches (see [3.8](#38-optional-services-calls-and-blockchain)
and [3.9](#39-email-smtp-and-the-mail-relay)), and exports `CG_CGID_VHOST`
(`on` only with `CG_LEGACY_CGID=true` and a `CG_ID_DOMAIN`).
Commands:

| Command | Action |
|---|---|
| `build` | builds the builder image, installs frontend deps, then type-checks, lints, builds and HTML-rewrite-checks the frontend in one builder run (`yarn typecheck && yarn lint && yarn build && yarn check:html-rewrite`, `DEPLOYMENT=prod`, `NODE_OPTIONS=--max-old-space-size=4096`), rsyncs `build/` into `caddy/dist`, builds the caddy / backend / db images — the backend with the build ID the frontend build drew (`build/build-id.txt` → `--build-arg CG_BUILD_ID`, [docs/infrastructure](../infrastructure/README.md#build-id); the checkout stays unmodified) — and generates `vapid_keys.json` for web push if missing (`umask 077`: mode `600`; the api reads it as root). Then, like `up`, it checks the modes of the secret files (`.env.selfhost`, `vapid_keys.json`, `s3_config/s3.selfhost.json`, `selfhost/certs/server.key`): one that others can read is set to `600` when the current user owns it, else a warning names it (`check_secret_modes`) |
| `up` | on a restore drill (`CG_BACKUP_DRILL=true`) prints a `DRILL INSTANCE` banner (mail is then forced off for every command, see [3.7](#37-backup-and-restore)); warns about mail settings that can't work together (see [3.9](#39-email-smtp-and-the-mail-relay)), about an ignored `CG_ID_DOMAIN` and about a `CG_PUBLIC_IP` that is empty or not IPv4, refuses a gateway that is not set up (`CG_ENABLE_GATEWAY=true` without its own domains and session secret, or with `CG_DOMAIN` under the gateway's domain, see [3.13](#313-the-gateway-of-a-moved-instance)), then `compose up -d --remove-orphans`, stops and removes the containers of switched-off optional services (`compose rm -sf`), and `ps` |
| `down` | stop the stack (`--remove-orphans`) |
| `logs [service]` | follow logs (all, or one service) |
| `ps` | container status |
| `stats` | `docker stats --no-stream` |
| `compose <args>` | pass-through to docker compose |
| `update` | `git pull`, then continues in the pulled script: rebuild, the mail, edge and gateway checks, the same start as `up`, and `ps` |
| `mail-dns` | prints the SPF, DKIM, DMARC and PTR records the built-in mail relay needs (see [3.9](#39-email-smtp-and-the-mail-relay)) |
| `backup init\|run\|list\|check\|verify\|install-timer\|uninstall-timer` | backups, handled by `docker/selfhost/backup.sh` (see [3.7](#37-backup-and-restore)) |
| `restore …` | restores a backup or a dump file (see [3.7](#37-backup-and-restore)); runs before `.env.selfhost` exists too (a new server gets it back from the backup) |

The frontend build is **Vite** (see
[docs/infrastructure](../infrastructure/README.md#frontend-build-steps) for the
full step list and the output layout). Two things changed for self-hosters with
the CRA removal:

- **Sourcemaps now ship**, on this path too. The old `GENERATE_SOURCEMAP=false`
  dated from the closed-source era; the app is AGPL, so shipping maps is
  intentional. They are excluded from the service-worker precache, so they cost
  bandwidth only when someone opens devtools. Scope: **JS maps only** — Vite
  emits no `.css.map` (CRA did).
- **Type errors and lint errors fail the build again.** The webpack build used
  to run both checks inline; a Vite build does neither, so `selfhost.sh build`
  runs them as explicit steps before `vite build`.

`NODE_OPTIONS=--max-old-space-size=4096` stays set on every build path: node
derives its default heap from machine RAM, and under Vite 7 a plain
`vite build` OOMed at 2048 MB and peaked at ~4 GB container RSS (≈3.9 GiB by
`docker stats`, ≈4.1 GiB cgroup peak, Node 24). Since Vite 8 (wave M3) the
build peaks at ~2.65 GiB cgroup `memory.peak` on Node 26 and passes with a
2048 MB heap too (measured 2026-11-01), so a host needs ~3 GB of free memory
for it rather than ~4 GB
(see [docs/infrastructure](../infrastructure/README.md#frontend-build-steps)).

### 3.3 Services (`docker-compose.selfhost.yml`)

All services share the internal `cryptogram` network, except the mail relay,
which sits on two networks of its own: `mail-relay` (`internal: true`; only
`api`, `job-runner`, `gateway-api` and `mail` join it) and `mail-egress` (its
way out to port 25; its bridge is named `cg-mail-out` so a host rule can single
it out, [3.11](#311-server-hardening)), and the build helper `cg-builder`, which
is only on its own `builder` network: the build needs the package registry,
never the stack's database, Valkey, storage or onchain service. State lives in named volumes (`pgdata`, `seaweedfs-data`, `caddy-data`,
`caddy-config`, `builder-cache`, `mail-data`).

| Service | Image | Role |
|---|---|---|
| `caddy` | `cryptogram/caddy-selfhost` (built from `docker/caddy/`; base `caddy:2.11.x-alpine`, exact tag + digest in its Dockerfile) | the edge: TLS (Let's Encrypt, or its local CA with `CG_TLS_MODE=internal`), static frontend, routing to API / wsapi / S3 / mediasoup, security headers and CSP, `/instance-config.js`; publishes `80`, `443` (tcp+udp), and `4443` with calls |
| `db` | `cryptogram/db:18` (PostgreSQL 18, `postgres:18-alpine` line; exact tag + digest in `docker/db/Dockerfile`) | primary database; `pgdata` mounted at `/var/lib/postgresql` (cluster in `18/docker`); init script creates the database and the `writer`/`reader`/`mediasoup` roles; loads tuned `postgresql.conf`; healthcheck; `shm_size 256m` |
| `redis` | `valkey/valkey:9.1-alpine` line (exact tag + digest in the compose file) | state instance: sessions, the Socket.IO adapter, rate limits, replay guards; password-protected, `noeviction`, RDB snapshots in `valkey-data`, `maxmemory ${REDIS_MAXMEMORY:-1024mb}`; no host port |
| `redis-cache` | same image | cache instance (URL previews): password-protected, `allkeys-lru`, unpersisted, `maxmemory ${REDIS_CACHE_MAXMEMORY:-256mb}`; no host port |
| `seaweed` | `chrislusf/seaweedfs` 4.x (exact tag + digest in the compose file) | SeaweedFS object storage — one all-in-one `weed server` (master + volume + filer + S3 gateway, aliased `s3.local`); only the S3 port 8333 is consumed by other services. `s3.selfhost.json` is mounted at `/run/cg/s3.json`; a small entrypoint copies it, as root, to `/etc/seaweedfs/s3.json` owned by the image's `seaweed` user (mode 600) and then runs the image's entrypoint, which drops to that user — the host file stays mode 600 whoever owns it |
| `migrate-db` | `cryptogram/backend` | one-shot DB migration (`migrateDb.js`); starts once `db` is healthy, `restart: on-failure:3`; the image's health check is disabled for it. Every backend service (`api`, `wsapi`, `memberlist`, `job-runner`, `onchain`, `mediasoup`, and the gateway's `gateway-api`, `gateway-wsapi`) starts only after it exited 0 — see "Migrations during an update" below |
| `api` | `cryptogram/backend` | REST API (`api.js`); the image everything else reuses |
| `wsapi` | `cryptogram/backend` | Socket.IO / real-time server (`wsapi.js`) |
| `memberlist` | `cryptogram/backend` | member-list worker (`memberlist.js`) |
| `job-runner` | `cryptogram/backend` | scheduled jobs incl. Spark accrual (`jobs.js`) |
| `mediasoup` | `cryptogram/backend` | WebRTC media (`mediasoup.js`); publishes `40000-40099` over UDP **and** TCP (each worker's `WebRtcServer` listens on `40000+n` for both; TCP is the ICE fallback for UDP-blocking networks); uses the internal self-signed cert and `MEDIASOUP_ANNOUNCED_IP=CG_PUBLIC_IP`. Starts only after `migrate-db` completed successfully — the `mediasoup` DB role comes from `docker/db/init.sh`, but its table privileges come from the migrations. Compose profile `calls` — optional, see [3.8](#38-optional-services-calls-and-blockchain) |
| `onchain` | `cryptogram/backend` | blockchain indexer / balance & role listener (`onchain.js`); receives all `QUIKNODE_*`/RPC and staking env. Compose profile `blockchain` — optional, see [3.8](#38-optional-services-calls-and-blockchain) |
| `mail` | `foxcpp/maddy:0.9.6` (pinned by digest) | send-only SMTP relay: accepts the app's mail on `mail-relay` port 587, DKIM-signs, queues and delivers to the recipients' MX. No published port. Compose profile `mail` — optional, see [3.9](#39-email-smtp-and-the-mail-relay) |
| `gateway-api` | `cryptogram/backend` | the gateway's REST API (`api.js` with `CG_GATEWAY=true`, `CG_LEGACY_CGID=true`, its own `BASE_URL`/`CGID_URL`/`REDIS_SECRET`, `TRANSFER_TARGET_URL` = this instance; no S3 credentials); joins `mail-relay` for email-code sign-in. Compose profile `gateway` — optional, see [3.13](#313-the-gateway-of-a-moved-instance) |
| `gateway-wsapi` | `cryptogram/backend` | the gateway's Socket.IO server (`wsapi.js`, same gateway settings). Compose profile `gateway` |
| `cg-builder` | `commonground/node` | build-only helper container (not a runtime service); network `builder` only |

The seven runtime `cryptogram/backend` services (nine with the gateway) are the same image invoked with
different `command` entrypoints and `DB_TYPE` roles (`writer` for most,
`mediasoup` for the media server). Each long-running one reports real health
— its database, Valkey (where it uses it) and its own listener; `selfhost.sh
ps` shows `healthy`/`unhealthy`, `docker inspect` the failing probe — see
[docs/infrastructure](../infrastructure/README.md#backend-health-checks).
Every service has a memory limit and rotating logs, and every backend process caps its
PostgreSQL pool with `PG_POOL_MAX` ([§5](#5-resource-footprint--tuning)).

**Migrations during an update.** On `selfhost.sh up` and `update`, Compose
first recreates every backend container whose image changed (the old ones are
stopped then), runs `migrate-db`, and starts the new backend containers only
once it has exited 0. **The app is unavailable while the migrations run.**
Measured on the e2e instance (2026-11-02, a test image with a pending 25 s
migration): the API stopped answering when `up` began and answered again 2 s
after `migrate-db` had finished; on a fresh install every backend service
started after `migrate-db` finished. **A failing migration** leaves the new
backend containers created but not started, and the old ones are already
gone — the instance stays down; the schema is unchanged, since all pending
migrations run in one transaction. `migrate-db` is retried three times
(`restart: on-failure:3`). Compose's own exit code did not reliably report it
(0 in one of two runs), so `selfhost.sh` checks `migrate-db`'s outcome after
`up` and stops with a message pointing at `selfhost.sh logs migrate-db`; fix
the cause or go back to the previous version (`git checkout <previous
commit>`, `selfhost.sh build`, `up`).

### 3.4 TLS (Caddy)

`docker/caddy/Caddyfile.selfhost` (routing and headers shared with the dev
stack in `common.caddy`, see
[docs/infrastructure §3](../infrastructure/README.md#3-caddy-the-edge))
defines, all from env:

- `CG_DOMAIN` — the app: static frontend, API,
  Socket.IO, `/files/`, share pages, instance config.
- `CG_DOMAIN:4443` → `reverse_proxy https://mediasoup:4443` for call
  signalling, only with `CG_CALLS_EDGE=on` (set, together with publishing
  the port, by `docker-compose.selfhost.calls.yml`); the internal hop trusts
  mediasoup's self-signed certificate (`tls_insecure_skip_verify`) while
  clients only ever see Caddy's certificate. Because signalling only arrives
  through Caddy, the compose file sets `MEDIASOUP_TRUST_PROXY=true` on
  `mediasoup`, so its per-client connection limits use the address Caddy puts
  in `X-Forwarded-For`.
- `CG_ID_DOMAIN` — the legacy CG ID mini-app, only with `CG_CGID_VHOST=on`
  (this instance itself in legacy CG ID mode); off on every normal instance.
- `CG_GATEWAY_DOMAIN` and `CG_GATEWAY_ID_DOMAIN` — the gateway of a moved instance and its CG ID
  app, only with `CG_GATEWAY_EDGE=on` (`CG_ENABLE_GATEWAY=true`, [3.13](#313-the-gateway-of-a-moved-instance)).

`CG_TLS_MODE` (passed to the `caddy` service, default `acme`) selects one of
two snippets that the global options block imports
(`import tls_mode_{$CG_TLS_MODE:acme}`):

- `acme` — the global `email {$CG_ACME_EMAIL}`; Caddy obtains and renews
  certificates automatically for the public domain (which must resolve to
  the server).
- `internal` — the global `local_certs` + `skip_install_trust`: every site,
  the `:4443` one included, gets a certificate from Caddy's local CA (root
  valid ~10 years; intermediate and leaf certificates are short-lived — leaf
  12 h — and renewed by Caddy). The root lives in the `caddy-data` volume at
  `/data/caddy/pki/authorities/local/` and must be trusted by every client
  browser. For LAN/test instances without public DNS — see
  `docker/SELFHOST.md` ("Local test instance") for trusting the root and for
  reusing one root across reinstalls by pre-seeding `root.crt`/`root.key`
  into a fresh volume.

Any other value fails at Caddy startup (`File to import not found`).

### 3.5 The Caddy image

`docker/caddy/Dockerfile`: the pinned stock Caddy image (no plugins), the
frontend build in `/srv`, the Caddyfiles and the instance-config template.
Nothing instance-specific is baked in — no build args, no config templating —
so the image does not depend on the domain; `robots.txt` gets its `Sitemap:`
line per request. Upstreams (`api`, `wsapi`, `s3.local`, `mediasoup`) are
resolved per connection, so Caddy starts even if a backend container is not
up yet. HSTS (`max-age=31536000`, no preload) is sent on the self-host sites,
error responses included.
Stock Caddy has no rate-limit handler, so there are no edge rate limits;
rate limiting is the backend's job.

### 3.6 Firewall

| Port | Protocol | Purpose |
|---|---|---|
| 80 | tcp | HTTP → HTTPS redirect, ACME |
| 443 | tcp+udp | app (HTTPS / HTTP3; also the CG ID site on a legacy gateway) |
| 4443 | tcp | call signalling (wss) — only with calls enabled |
| 40000–40099 | udp+tcp | WebRTC media (voice/video); TCP is the fallback for clients whose network blocks UDP — only with calls enabled |

Outbound, the built-in mail relay needs **port 25** to the internet (only with
`CG_ENABLE_MAIL=true`; nothing inbound) — see [3.9](#39-email-smtp-and-the-mail-relay).

These are the only host ports the self-host compose files publish (checked
with `docker compose config`: caddy `80`, `443` tcp+udp, `4443`; mediasoup
`40000-40099` tcp+udp). Ports Docker publishes are opened in Docker's own
netfilter chains, **in front of** a host firewall such as ufw, so they are
reachable whatever ufw says — which is why nothing else may be published
(a service that must be reachable from the host only binds to `127.0.0.1`).
`docker/selfhost/harden.sh` ([3.11](#311-server-hardening)) sets ufw up for
exactly this table plus SSH and lists any published port outside it.

### 3.7 Backup and restore

`selfhost.sh backup …` / `selfhost.sh restore …` hand over to
`docker/selfhost/backup.sh` (before the `.env.selfhost` check, so a restore
can run on a server that has none yet). The operator guide is
[`docker/SELFHOST.md`](../../docker/SELFHOST.md#backup-and-restore); this
section records how it works and why.

**Format.** One backup is one [restic](https://restic.net) snapshot (tag
`cg-backup`, host `CG_BACKUP_HOST`, default `CG_DOMAIN`) with the paths
`/cg/MANIFEST` (format `cg-backup-1`, time, domain, git commit, PostgreSQL
version, newest migration, SHA-256 of the dump, component list), `/cg/db/`
(`cryptogram.pgc` = `pg_dump -Fc -Z 0`, uncompressed so restic can deduplicate
and compress it, plus `rowcounts.txt`), `/cg/secrets/` (`.env.selfhost`,
`vapid_keys.json`, `s3_config/s3.selfhost.json`, `selfhost/certs/`,
`backup/` — paths relative to `docker/`), `/cg/media/` (the `seaweedfs-data`
volume), `/cg/caddy/` (`caddy-data`) and `/cg/mail/dkim_keys/` (from
`mail-data`). Every snapshot also carries the tag `machine-<id>` (a hash of
`/etc/machine-id`, or `CG_BACKUP_MACHINE_ID`) of the server that made it. restic runs in the official `restic/restic` image, pinned by
version and digest in the script (`RESTIC_IMAGE`; a Renovate regex manager
tracks it), which also serves as the helper for file operations inside
volumes; the host needs only Docker and `flock`.

**Repositories.** The snapshot is written to a local repository
(`CG_BACKUP_DIR/repo`, default `/var/backups/commonground`; created on first
use owned by the checkout owner, mode 700) and then `restic copy`-ed to
`CG_BACKUP_REPOSITORY` (any restic URL; documented for SFTP storage boxes and
S3) — each local snapshot of this host exactly once, chosen by identity: the
copied ids are recorded in `CG_BACKUP_DIR/copied-<key>` (seeded from the
remote copies' `original` field when missing). Copying "all local snapshots"
re-copied the local oldest one (restic ≥ 0.17 keeps it while a keep bucket is
not full) after every take-over, only for the remote retention to prune it
again; selecting "newer than the remote's newest" depended on two servers'
clocks. Both repositories share chunker parameters
(`init --copy-chunker-params`, from whichever exists first), otherwise every
copy would store the data again. Retention (`forget --prune --group-by host`,
default 7 daily / 4 weekly / 6 monthly, only this host's snapshots) runs on
both after every backup — on the remote only with
`CG_BACKUP_REMOTE_RETENTION=true` (default); `false` is for an append-only
target whose retention runs elsewhere. **Timeline guard:** `backup run`
refuses to write into a repository that holds snapshots of the same
`CG_BACKUP_HOST` with another server's machine tag that this server has not
accepted (by id, recorded in `CG_BACKUP_DIR/guard-<key>`; refreshed after each
successful run) — checked on both repositories before the dump, so a refused
run writes nothing; if the remote cannot be read within 120 s the local
backup still runs and the remote is checked again before the copy.
`--take-over` accepts the other server's snapshots once, after a restore onto
a replacement server; a snapshot that server makes afterwards is refused
again. Without an off-server repository each run prints a
warning and still succeeds. Everything is encrypted by restic with
`CG_BACKUP_PASSWORD` (generated by `init.sh`, or added to an older
`.env.selfhost` by `backup init`), which must also be kept off the server.

**Consistency.**

- Database: `pg_dump` runs against the live database with a snapshot
  exported from a `REPEATABLE READ` transaction (`pg_export_snapshot()`), and
  the exact row count of every table is taken inside that same transaction —
  so the counts describe exactly the dump, and a restore can compare them.
- Media: SeaweedFS has no online-consistent backup (a copy can catch the filer
  leveldb mid-change). Options considered: an S3-level copy (`rclone`/`mc`;
  online and backend-neutral, but a third tool, slower for many small
  objects, and object metadata such as the content type does not survive a
  plain file copy), `weed filer.backup` / `weed backup` (online, but a
  different restore path per volume and more moving parts), stopping the
  container (consistent, but measured 2026-11-01: its shutdown hangs in the
  gRPC graceful stop and is killed after Docker's 10 s grace period, and a
  restart takes ~17 s until files are served again) — and **`docker pause`**,
  which the script uses: the container is frozen while restic reads the
  volume, so the copy is crash-consistent like the killed stop, but requests
  only wait instead of failing (verified with an 8 s freeze) and it resumes
  instantly. To keep the freeze short, a **warm-up pass** first backs up
  everything unfrozen (tag `cg-warmup`); the frozen pass uses it as
  `--parent`, so restic re-reads only files changed in between — mostly the
  volume file being appended to (up to `SEAWEED_VOLUME_LIMIT_MB`) and the
  filer's leveldb files — and the warm-up snapshot is forgotten afterwards
  (leftovers at the start of the next run). Measured: 1 s freeze with nothing
  changed in between, 2 s after 50 MB of uploads in between (a 100 MB volume
  file re-read). The dump is taken before the freeze, so the media copy is
  never older than the database. A seaweed left frozen by a killed run is
  resumed by `backup resume` (the units' `ExecStopPost`), by `selfhost.sh
  up`/`update` and by the next backup. `pg_dump` runs with
  `--lock-wait-timeout=5min`.
- Valkey is not backed up: everything in the state instance is short-lived
  (sessions, rate-limit windows, codes, replay guards, presence), and
  restored sessions would belong to another point in time. A database restore
  removes `valkey-data`.
- `caddy-data` is backed up and restored (if the target is empty, or with
  `--force`): it avoids re-issuing Let's Encrypt certificates (duplicate-cert
  rate limit) and keeps the local CA of a `tls internal` instance that clients
  already trust.

**Restore.** `restore [--from local|remote] [--only …] [--force]
[--with-secrets] [--drill] [--dry-run] <snapshot|latest>` first **plans
everything without changing anything**: secrets (missing files are restored,
identical ones left alone, differing ones kept unless `--with-secrets
--force` / `--only secrets --force`), database and media emptiness (a
non-empty one is refused without `--force`; `db` is started alone to look
inside, and the plan says so), and the dump itself (fetched, SHA-256 checked
against the manifest, roles it needs compared with the cluster's). Only then
does it apply: secrets, stop the stack, and for the database start `db`
alone, set the passwords of `postgres`, `writer`, `reader` and `mediasoup`
from the current `.env.selfhost` (via `\getenv` in psql, so they never appear
in a command line; creates missing roles), **rename** a non-empty database to
`cryptogram_pre_restore_<stamp>`, `pg_restore -j` from a one-off client
container in the `db` container's network namespace, `vacuumdb
--analyze-in-stages`, compare the row counts with the backup; volumes get
their current contents moved into `.pre-restore-<stamp>/` (a rename on the
same filesystem) before restic restores (`--verify`). The pre-restore copies
are dropped only after every component succeeded, so a `--force` restore
needs free space for a second copy of the database and media. Every step is
recorded in `docker/restore-undo.pre-restore-<stamp>` (volumes with a
"moving"/"moved" pair, so an undo after a crash in the middle only moves
entries back); on a failure the restore prints what it already replaced, that
the stack is stopped, and the commands to go back (`restore --undo <stamp>`,
idempotent; `--force` needed when services ran since) or to undo and retry.
After the last step the record is renamed to `….done` (the commit point)
before the copies are dropped; a failed or interrupted cleanup reports success
and points to `restore --discard-undo <stamp>`, never to an undo. A restore
refuses to start while an unfinished or `.done` record, a `.pre-restore-*`
volume entry or a `cryptogram_pre_restore_*` database exists, and refuses when
Docker's storage cannot hold ~3x the dump plus the media and caddy-data (or
`CG_BACKUP_DIR` the dump; `--ignore-space-check`). Restored secrets keep their
backed-up owner and mode; `.env.selfhost` and `backup/` go to the checkout
owner; an existing `backup/` is always kept. psql answers are checked (a
failing query is an error, never "empty"), and so are the mail-volume probes. When the restored `.env.selfhost` changed but the database is not part
of the restore, the role passwords are still set from it. Because the role
passwords come from the current `.env.selfhost`, the database also works next
to fresh `init.sh` secrets (rehearsal servers). `--db-file <dump.pgc>`
restores a plain dump with the same rules (the import path roadmap G5 builds
on). `backup verify` is the restore drill that leaves the instance alone: it
restores a snapshot's dump into a throwaway PostgreSQL container (removed
with its volume afterwards) and compares the row counts.

**Drill mode.** `restore --drill` marks a drill or test copy: after the
secrets are restored it rewrites `.env.selfhost` — `CG_BACKUP_DRILL=true`,
the source repository moved to `CG_BACKUP_DRILL_SOURCE` with
`CG_BACKUP_REPOSITORY` emptied, `CG_BACKUP_HOST=drill-<hostname>`,
`CG_ENABLE_MAIL=false`, empty `SMTP_HOST`, `CG_TLS_MODE=internal` (no
renewals on production's ACME account). In drill mode the source is read
with `--no-lock` and never written (no init, copy, retention or `check`
there), the DKIM key is not restored, and `install-timer` is refused.

A drill must not reach the source's users. What could:

- *Web push.* The secrets bundle never brings the source's
  `vapid_keys.json` onto a drill: a missing one is generated fresh (inside
  the restic helper container: `ssh-keygen -t ecdsa -b 256 -m PEM`, the SEC1
  DER key checked for its fixed P-256 layout and turned into the
  `{"publicKey","privateKey"}` base64url JSON that `web-push
  generate-vapid-keys --json` writes; mode 600, checkout owner), one identical
  to the backup's (an earlier copy) is replaced by a fresh one (the old file
  stays as `vapid_keys.json.pre-restore-<stamp>`, undoable), the drill's own
  is kept — also with `--with-secrets --force`. Every database restore on a
  drill (snapshot or `--db-file`) then sets `devices."webPushSubscription"`
  to `NULL` (the only place push subscriptions are stored; the devices stay,
  they are login keys) after the row-count comparison; a failure there fails
  the restore. When a drill restore generates or renews the key pair without
  restoring the database, it clears the column in the database already in
  place (starting `db` alone; recorded as not undoable). Push services would
  reject the old subscriptions anyway (they are bound to the source's public
  key); clearing them keeps `sendWsOrWebPushNotificationEvent` from sending
  to them at all. The api reads the key pair once at start
  (`srv/repositories/notifications.ts`), so a drill restore of the secrets
  alone stops every running service before it changes anything (`up`
  recreates the containers whose settings changed); restores of other
  components stop the stack anyway.
- *Mail* (login codes, verification, notification and digest mails,
  newsletters, the bounce receiver): `CG_ENABLE_MAIL=false` and an empty
  `SMTP_HOST` in `.env.selfhost` (`emailEnabled()` is false, both mail jobs
  skip their work, no `mail` container, `MAIL_BOUNCE_RECEIVER=false`), and
  `selfhost.sh` enforces it: with `CG_BACKUP_DRILL=true` it exports
  `CG_ENABLE_MAIL=false` and `SMTP_HOST=` before every compose call, which
  win over the env file, so mail settings edited back into a drill's
  `.env.selfhost` have no effect. The DKIM key is never restored, and the
  relay's queue is not part of a backup.
- *Bots* have no outbound channel: they connect to the instance (bearer
  token, Socket.IO), the backend never calls them; bots configured with the
  source's URL keep talking to the source.
- *Plugins* are iframes in the viewer's browser; the backend verifies and
  signs the messages they relay through it but never calls a plugin URL.
- *Onchain/staking*: nothing signs or sends transactions — the `onchain`
  service reads (events, balances, token metadata) from the configured RPC
  endpoints, and staking accrual and premium renewal only write the drill's
  own database. A drill uses the source's RPC URLs, and so their quota.
- *Jobs* (`job-runner`): `premiumRenewal`, `callUpdateEmitter`,
  `handleCommunityAirdrops`, `onlineStatusCheck`, `stakingAccrual` and
  `activityScore` work on the database only (their notifications go out as
  WebSocket events to connected clients, and as web push only to
  subscriptions made on the drill); `emailNotifications` and
  `newsletterDelivery` need mail; `bounceReceiver` is off.
- Outbound requests that remain are made on behalf of someone using the
  drill: link previews, reCAPTCHA verification (when configured), X/Twitter
  and Farcaster login.

`--db-file … --drill` writes the same drill settings into `.env.selfhost`
(after stopping the stack, before the dump is restored; the instance's own
`CG_BACKUP_REPOSITORY` becomes the read-only `CG_BACKUP_DRILL_SOURCE`).

A restore on a drill ends with a summary of what it changed (the VAPID
outcome, the number of cleared subscriptions, stopped services) and the
mail, TLS and backup settings in effect — with a warning if `.env.selfhost`
lacks `CG_BACKUP_DRILL=true`. `selfhost.sh up`/`update` print a
`DRILL INSTANCE` banner that states only what `selfhost.sh` itself enforces
(mail off, local backups).

**Scheduling.** `backup install-timer` (root) writes `cg-backup.service` /
`.timer` (daily, `CG_BACKUP_SCHEDULE`, default 03:30) and
`cg-backup-check.service` / `.timer` (weekly `restic check` reading 5 % of the
data, `CG_BACKUP_CHECK_SCHEDULE`) to `/etc/systemd/system`. The services run
as the owner of the checkout (`User=`; `install-timer` checks with
`runuser` that it can read `.env.selfhost` and use Docker —
nothing in a backup needs root, restic itself runs as root inside its
container), with `TimeoutStartSec=${CG_BACKUP_TIMEOUT:-4h}`,
`NoNewPrivileges=yes`, `PrivateTmp=yes` and `ExecStopPost=-… backup resume`;
`install-timer` gives `CG_BACKUP_DIR` to that user (mode 700) only if it is
new or holds nothing but backup data; a non-root run that cannot enter it
stops at once. Failures before the EXIT trap (image pull, password, machine
id, lock, backup directory) still run `CG_BACKUP_ON_FAILURE`, once. Output goes to
the journal; failures exit non-zero and run `CG_BACKUP_ON_FAILURE`. A `flock`
on `/run/lock/cg-backup-<project>.lock` (no fallback location) keeps runs of
one instance from overlapping; a run that finds it taken logs that loudly,
runs the failure hook (backups) and exits 75. `selfhost.sh up`/`down`/`update`
take the same lock non-blocking (not the `compose` passthrough backup.sh
uses), and `backup resume` does nothing while it is held. Locked commands
first sweep leftovers of interrupted runs. The warm-up pass accepts restic
exit 3; the frozen pass does not. The machine tag comes from
`/etc/machine-id` or `CG_BACKUP_MACHINE_ID` — never from the hostname; cloned
VMs need a new machine-id (SELFHOST.md). `CG_BACKUP_DIR` inside the secrets bundle (e.g.
`docker/backup/`) is refused.

Verified 2026-11-01 on the development VM (throwaway stacks, 50–300 MB of
media): backup, same-server rollback with `--force`, restore onto a fresh
stack from the off-server copy (S3 and SFTP targets), restore of data into an
instance with its own secrets, `--db-file` incl. the missing-role refusal, a
restore failing after the database step (report, `--undo` back to the exact
previous state), drill mode (no writes or locks on the source, mail off,
timer refused), the timeline guard and `--take-over`,
`CG_BACKUP_REMOTE_RETENTION=false`, no volume left by `backup verify`, a
frozen seaweed resumed by `up` and `backup resume`; after the second
review also: secrets restored as a faked root caller keep their owners, the
new-server procedure exactly as documented (only `id_ed25519` and
`known_hosts` copied), a rerun refused after a failed restore, `--undo`
refused after `up` without `--force`, a crash in the middle of moving a volume
undone without loss, a failed and an interrupted cleanup after the commit
point (reported as success, removed with `--discard-undo`), `backup resume`
and `up`/`down` refused while the lock is held, warm-up exit 3 accepted and
frozen-pass exit 3 failing, the free-space refusal — each restore followed by
a password login, a signed `/files/` download, byte-identical media and
identical VAPID keys where the secrets were restored. After the third review:
no re-copy of an old snapshot after a take-over, no filters with an explicit
snapshot id, a quiet image pull on a fresh server, `CG_BACKUP_DIR` mode 700.
Drill isolation (same day, throwaway projects): a source with VAPID keys and
two push subscriptions restored with `--drill` from its repository — fresh
keys (65/32 bytes, the pair consistent, accepted by `web-push`, a VAPID JWT
verifying against the new public key), subscriptions 0 of 3 devices, row
counts matching; the `renew` case with `--only secrets --force`; the own key
kept on a later restore; `--db-file` on the drill clearing them too; mail
settings switched back on in the drill's `.env.selfhost` still giving no

`compose config`; a restore without `--drill` still bringing the source's
keys back.

**Restore rehearsal on the test VM, 2026-11-01: passed.** A new-server restore
following SELFHOST.md, `backup verify`, a same-server rollback and `--undo`

### 3.8 Optional services (calls and blockchain)

`mediasoup` and `onchain` carry the Compose profiles `calls` and `blockchain`.
`selfhost.sh` computes `COMPOSE_PROFILES` from two switches in `.env.selfhost`:

| Switch | Default | Effect when `false` |
|---|---|---|
| `CG_ENABLE_CALLS` | `true` | no `mediasoup` container; the instance config ships `features.calls: false`, so both call entry points hide: the community sidebar (`CallList` / `StartCallButton`) and the event path (`ScheduleEventModal` offers only `external` events, `AttendEventButton` drops "Start Event" / "Join now"). Ports 4443/tcp and 40000–40099/udp+tcp are not published |
| `CG_ENABLE_BLOCKCHAIN` | `true` | no `onchain` container; `CG_ENABLE_BLOCKCHAIN=false` also reaches the `api` process, where `OnchainHelper` fails fast with `SERVICE_UNAVAILABLE` instead of waiting out the 10 s HTTP timeout per request (the community role-claimability check the join and roles views make answers "nothing claimable" instead) |

Both default to on, so an `.env.selfhost` generated before these switches
existed keeps the full stack.

A third switch, `CG_ENABLE_IMAGE_FILTER` (default `true`), is not a Compose
profile: it disables the server-side NSFW image filter inside the `api` and
`onchain` services (`IMAGE_MODERATION_ENABLED`) and ships
`features.imageFilter: false` in the instance config, which also turns off
the client-side pre-upload warning. `CG_IMAGE_FILTER_THRESHOLD` and
`CG_IMAGE_FILTER_MODEL_PATH` tune the reject threshold and swap in another
Transformers.js-layout classifier (see
[docs/backend](../backend/README.md#srvmoderationimagefilterts--nsfw-image-gate)). `up` and `update` stop and remove the
container of a service whose switch is flipped off (`compose rm -sf`):
`--remove-orphans` does not, because a profile-disabled service is still part
of the compose file.

Without the `onchain` service: token-gated roles are no longer re-evaluated
(existing assignments stay, nobody is stripped), balances are not refreshed,
staking positions are not indexed, Spark purchases are not credited, LUKSO
Universal Profile login fails, and adding a new token contract returns a clean
`NOT_FOUND`. EVM/SIWE wallet login is unaffected — it is verified by signature
inside the `api` process and never calls the onchain service.

With calls disabled, `selfhost.sh` leaves out `docker-compose.selfhost.calls.yml`:
Caddy has no `:4443` site and the port is not published.

The mail relay has a profile of its own (`mail`, switch `CG_ENABLE_MAIL`), with
the opposite default — see [3.9](#39-email-smtp-and-the-mail-relay).

### 3.9 Email (SMTP and the `mail` relay)

The backend sends every mail over SMTP (nodemailer; configuration and the mail
types in [docs/email-notifications](../email-notifications/README.md)). The
`api` and `job-runner` services get `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURITY`
(`tls` | `starttls` | `none`), `SMTP_USER`, `SMTP_PASSWORD`, `EMAIL_FROM` and
`EMAIL_FROM_NAME` from `.env.selfhost`; an empty `SMTP_HOST` disables email.
`CG_ENABLE_NEWSLETTERS=false` pauses digest/article newsletters independently of
SMTP; set it on both API and job-runner via the supplied Compose configuration.
Queued articles and subscriptions are retained. Login, security and event mails
continue.

Two ways to give it an SMTP server:

**Built-in relay — `CG_ENABLE_MAIL=true`** (what `init.sh` writes). The `mail`
service (profile `mail`) runs [maddy](https://maddy.email) with the config in
`docker/mail/` (`maddy.conf`, `outbound.conf`, `entrypoint.sh`, bind-mounted
read-only):

- The app submits on port 587 over the `mail-relay` network with
  `SMTP_HOST=mail`, `SMTP_SECURITY=none` and the relay login `SMTP_USER` /
  `SMTP_PASSWORD` (generated by `init.sh`). The same two variables configure
  the relay side: `entrypoint.sh` hashes the password for maddy's
  `pass_table` at every start. Plaintext on that hop is deliberate — the
  network is internal and reachable only by `api`, `job-runner` and `mail`.
- Sender restrictions: unauthenticated submissions are refused, and an
  authenticated one only for envelope and `From` addresses in `MAIL_DOMAIN`
  (`authorize_sender`; default `CG_DOMAIN`, must equal the domain of
  `EMAIL_FROM`).
- DKIM: maddy signs every message with the key
  `/data/dkim_keys/<MAIL_DOMAIN>_<MAIL_DKIM_SELECTOR>.key` (selector default
  `cg`), which it generates (RSA 2048) on the relay's first start. The key
  exists only in the `mail-data` volume — never in an app container. The
  signature covers the RFC 8058 `List-Unsubscribe`/`List-Unsubscribe-Post`
  headers too.
- Delivery: a persistent queue (`/data/outbound_queue` in `mail-data`) retries
  temporary failures (greylisting, outages) with exponential back-off, 20
  attempts over about three days; `outbound.conf` delivers to the recipient's
  MX over port 25, IPv4 only (`force_ipv4`, so the PTR check runs against the
  IPv4 address), requiring TLS towards the MX (`min_tls_level encrypted`) and
  honouring MTA-STS. The relay is the only component that sends to port 25.
  The compose file alone does not enforce it (`api` and `job-runner` have
  ordinary outbound access on `cryptogram`); `harden.sh`'s `mail25` part does,
  with a `DOCKER-USER` rule that refuses outgoing 25/tcp from every Docker
  bridge except the relay's `cg-mail-out` ([3.11](#311-server-hardening)).
- Bounces: a permanent failure becomes a delivery status notification to
  `EMAIL_FROM`; the queue's `bounce` block routes it through `bounce_queue`
  (retries while the job-runner is down) to the job-runner's bounce receiver
  (`target.smtp` to `job-runner:2525` over `mail-relay`, same relay login).
  The job-runner is also on `cryptogram`, so the receiver only accepts
  connections from the address(es) the host name `mail` resolves to. Bounces
  are recorded in `email_bounces`; an address is marked unverified (which
  stops all further notification mail to it) only after two permanent
  bounces at least 24 h apart, and never during a burst of bounces, which
  points to a problem of the server itself (blocklist, SPF/DKIM/DMARC, PTR)
  and is logged with a `!!!` warning — see
  [docs/email-notifications](../email-notifications/README.md#bounces). The
  `job-runner` runs the receiver when `MAIL_BOUNCE_RECEIVER=true`, which the
  compose file sets from `CG_ENABLE_MAIL`.
- Limits: submissions are capped at 50 messages/s and 10 in parallel; maddy
  has no cap on the queue size. Per-user send limits live in the app
  ([docs/email-notifications](../email-notifications/README.md#send-limits)).
- `MAIL_HOSTNAME` (default `CG_DOMAIN`) is the name it greets other servers
  with; the server IP's PTR record must point to it.
- The container runs read-only with all capabilities dropped and no published
  port. maddy logs two "insecure configuration" warnings at start (no TLS,
  plaintext AUTH on the listener) — expected for the internal-only listener.

`./selfhost/selfhost.sh mail-dns` reads the generated public key (a throwaway
container on `mail-data`) and prints the records to publish: SPF
(`v=spf1 ip4:<CG_PUBLIC_IP> -all`), the DKIM TXT record (split into ≤ 250
character strings for zone files), a starting DMARC policy (`p=none`, strict
alignment) and the PTR/forward-confirmation pair. Two things outside DNS decide
whether the relay delivers at all: the hoster must allow **outbound port 25**
(many block it for new servers until asked), and a fresh IP has no sending
reputation — start with low volume and watch the logs
(`./selfhost/selfhost.sh logs mail`).

**External SMTP server — `CG_ENABLE_MAIL=false`.** No relay container; set the
`SMTP_*` values to the provider's (e.g. `SMTP_SECURITY=starttls`, port 587, or
`tls` on 465). SPF/DKIM are then the provider's business, and so are bounces:
they go to the provider's bounce handling or the `EMAIL_FROM` mailbox, and the
app does not read them.

Unlike calls and blockchain, an **unset** `CG_ENABLE_MAIL` counts as off, so
upgrading an instance whose `.env.selfhost` predates the switch never starts
sending mail from the server before its DNS is set up. `selfhost.sh up` (and
`update`) warns, without failing, when the switches contradict each other:
relay on but `SMTP_HOST` not `mail`, relay on without a relay login, a sender
(`EMAIL_FROM`, or its default `no-reply@CG_DOMAIN`) outside `MAIL_DOMAIN`,
`SMTP_HOST=mail` with the relay off, `SMTP_SECURITY=none` towards a host that
is neither loopback nor a single-label service name, or leftover
`SENDGRID_API_KEY` / `MAILCHIMP_API_KEY` values (both unused since email moved
to SMTP) — with an explicit "email is disabled" warning when `SMTP_HOST` is
still empty (the SendGrid-over-SMTP recipe is in `docker/SELFHOST.md`).

### 3.10 IPv6

The stack runs IPv4-only: its Docker networks have no IPv6, and mediasoup
listens on `0.0.0.0` and announces `CG_PUBLIC_IP`. Docker still accepts IPv6
connections on the published ports, but forwards them through its userland
proxy (`docker-proxy`), which connects to the container over IPv4 **from the
bridge gateway's address**. Measured on the dev VM (Docker 29.9.2,
2026-11-02, a listener on an IPv4-only network behind `-p [::1]:…`): the
container saw the connection from `172.21.0.1`, the gateway. Behind an AAAA
record, Caddy would therefore see every IPv6 visitor as one client — the
backend's per-address limits (sign-ups, login throttles, the API rate limit)
would be shared by all of them, and the logs would lose their addresses.

Hence `init.sh` records the server's IPv6 address (`CG_PUBLIC_IPV6`) but tells
the operator to publish an **A record only**. Calls stay on IPv4 as well;
clients on IPv6-only networks depend on their provider's IPv4 translation
(464XLAT, as common on mobile networks) — TODO(verify): a call from an
IPv6-only network.
The mail relay sends over IPv4 only, so `mail-dns` asks for no `ip6:` SPF
entry and no IPv6 PTR record. Native IPv6 (IPv6 on the `cryptogram` network,
so published ports are NATed with the client's real address, and an IPv6
listen address for mediasoup) is a follow-up in `docs/todo/TODO.md`.

### 3.11 Server hardening

`docker/selfhost/harden.sh` is the base setup of a dedicated Ubuntu/Debian
server (roadmap S3; the Ansible suite takes it over after the move). It is
idempotent — a second run reports every part `[ok]` and changes nothing — and
`--dry-run` prints each change it would make (file diffs, commands) without
touching the system; without root a dry run reads what it can. `--skip <part>`
leaves out `ssh`, `firewall`, `upgrades`, `logs`, `sysctl` or `mail25`. Exit code 1 when
a part failed or was refused.

| Part | What it does |
|---|---|
| `ssh` | writes `/etc/ssh/sshd_config.d/10-commonground.conf`: `PasswordAuthentication no`, `KbdInteractiveAuthentication no`, `PermitEmptyPasswords no`, and `PermitRootLogin prohibit-password` **only** when root login was fully open (effective `yes`) — a stricter value (`no`, `forced-commands-only`) stays; once written the line is kept, so a second run changes nothing. sshd uses the **first** value it reads, and the file sorts before the `50-cloud-init.conf` that cloud images ship with `PasswordAuthentication yes`. **Refused** unless the operator account — `--ssh-user`, else the login user of the session (`/proc/self/loginuid`, which survives `sudo` and `sudo su -`), else `$SUDO_USER` — has a usable key: valid, not bound to a forced command (`command="…"`), in an `AuthorizedKeysFile` as sshd resolves it for that user, with file, directory and home not writable by others or owned by someone else (StrictModes). Also refused without a past key login of that account in the journal or auth log (`Accepted publickey for <user>`, last 90 days; `--no-login-check` skips this) and when `sshd_config` does not include `sshd_config.d/*.conf`. Validated with `sshd -t` (the file is removed again if that fails), then sshd is reloaded and the effective values are read back with `sshd -T`. |
| `firewall` | ufw. SSH first: the ports sshd's configuration names (`sshd -T` `listenaddress` lines), the ports sshd — or an active `ssh.socket` — listens on (`ss`, `systemctl show -p Listen ssh.socket`) and the server port of every SSH session (`$SSH_CONNECTION`, established sshd connections) must agree; otherwise (a changed but not yet applied configuration, a socket override, a forwarded port) the part stops **without touching ufw**. Then `80/tcp`, `443/tcp`, `443/udp`, `4443/tcp`, `40000:40099/udp`, `40000:40099/tcp`; default deny incoming / allow outgoing; enable. IPv4 and IPv6 rules: with `IPV6=no` in `/etc/default/ufw` (IPv6 unfiltered), the part stops a running ufw, switches it to `yes`, adds every rule again and enables it. Lists every port a running container publishes outside this set (Docker-published ports bypass ufw, [3.6](#36-firewall)) and warns when Docker uses its nftables firewall backend (Docker 28+; not tested together with ufw). The routed (forward) policy stays ufw's default; Docker manages its own forwarding chains. |
| `upgrades` | installs `unattended-upgrades` and enables the daily run (`/etc/apt/apt.conf.d/20auto-upgrades`) with the distribution's default origins — security updates, installed as soon as they are published (a standing exception to the waiting periods, [UPDATE-POLICY.md](../infrastructure/UPDATE-POLICY.md#standing-exception-the-hosts-distribution-security-updates)). The container runtime is excluded (`/etc/apt/apt.conf.d/51commonground-unattended-upgrades`: `docker.io`, `docker-ce*`, the Compose and Buildx plugins, `containerd*`, `runc`) — updating it restarts every container, so it is done by hand. No automatic reboot: a pending one is reported. |
| `logs` | journald capped at 1 GB and four weeks (`/etc/systemd/journald.conf.d/90-commonground.conf`); `logrotate` installed (it ships with both distributions' server images). Container logs rotate through the compose files ([§5](#log-rotation)). |
| `sysctl` | `/etc/sysctl.d/90-commonground.conf`: `net.ipv4.ip_local_reserved_ports = 40000-40099` (the ephemeral port range overlaps the media ports, and a collision keeps mediasoup from starting) and `vm.overcommit_memory = 1` (the Valkey state instance forks for its snapshots); loaded at once and checked. |
| `mail25` | outgoing 25/tcp from containers only through the mail relay's network: `/usr/local/sbin/cg-mail-egress` inserts, idempotently, `-i docker0` and `-i br-+ -p tcp --dport 25 -j REJECT --reject-with tcp-reset` (comment `cg-mail-egress`) at the top of Docker's `DOCKER-USER` chain, for `iptables` and, where Docker has the chain, `ip6tables`; the relay's bridge `cg-mail-out` matches neither. The script applies the rule only while the interface `cg-mail-out` exists; without it (a relay network created before the bridge had a fixed name is `br-<id>`) it removes its rules and exits 1, and the part, with Docker running, warns and sets nothing up — SELFHOST.md has the steps to recreate the network. `cg-mail-egress.service` (oneshot, `After=`/`PartOf=`/`WantedBy=docker.service`) applies it whenever Docker starts, so it survives reboots and Docker restarts; the part enables the unit and applies the rule at once when Docker runs. Needs Docker's iptables firewall backend (on Ubuntu 26.04 `iptables-nft`, which provides `DOCKER-USER` the same way); with the nftables backend the part warns and sets nothing up (SELFHOST.md has an nftables equivalent), and the script exits non-zero when the chain is missing, so the unit shows as failed. Leave it out when the instance sends through another server on port 25. |

A file that cannot be written is reported as `[FAILED]`; `--ssh-user`
without a name is a usage error (exit 2).

Not covered: fail2ban (key-only SSH leaves nothing to brute-force) and the
hoster's own firewall. The `mail25` rule script was tested 2026-11-07 in an
`alpine:3` container's own network namespace (`iptables-nft`, a `DOCKER-USER`
chain and a dummy `cg-mail-out` link created by hand): two runs leave exactly
two rules per family, without the link no rule is applied and existing ones
are removed (exit 1); the part itself was dry-run on Ubuntu 26.04 with
Docker 29.9 (iptables backend). The real run on a server with Docker is
still to be done on the test VM.
Tested 2026-11-02 in throwaway `ubuntu:26.04` and `debian:13` containers (own
network namespace, a running sshd, no `--privileged`): dry runs as root and
non-root, `--ssh-user` without a value, the refusals (no key, only a
forced-command key, a group-writable `~/.ssh`, no key login in the auth log),
a real run and the idempotent second run, sshd's effective settings with a
`50-cloud-init.conf` present, `PermitRootLogin yes` (restricted, then
unchanged) and `no` (left alone), `ListenAddress 0.0.0.0:2222` before and
after sshd's restart (refused, then 2222 allowed), a session on a port sshd
does not listen on (refused), an `ssh.socket` on another port (systemctl
shim; refused), `IPV6=no` (switched, IPv6 rules added), the operator from the
login uid in a `sudo su -` style root shell, the published-port and
nftables-backend checks (docker shim) and the runtime blacklist as `apt-config`
reads it. The sysctl step cannot take effect in a container (read-only
`/proc/sys`), and reloading sshd, journald and the real `ssh.socket` need
systemd — their test is the first run on the test VM.

### 3.13 The gateway of a moved instance

For the move of the hosted instance (app.cg → cg.box) the new instance serves the old domain as a
sign-in-only gateway ([docs/auth-identity §12](../auth-identity/README.md#12-gateway-mode); operator
guide: [`docker/SELFHOST.md`](../../docker/SELFHOST.md#gateway-for-a-moved-instance)). Design: the
simplest that fits one server and one edge —

- **Backend**: two more services from the same image, `gateway-api` and `gateway-wsapi`, under the
  Compose profile `gateway` (`CG_ENABLE_GATEWAY=true`), on the same `db` and `redis` (writer role,
  like api; a narrower database role is possible later). No storage credentials: no route the
  gateway serves reads or writes files (LUKSO and Farcaster refuse an unknown account before any
  profile image is fetched).
  Only api and wsapi: job-runner, onchain, memberlist, mediasoup and migrate-db run once, for this
  instance, and refuse to start in gateway mode.
- **Edge**: the same Caddy, two more sites (`CG_GATEWAY_DOMAIN`, `CG_GATEWAY_ID_DOMAIN`; snippet
  `cg_gateway_app` and the CG ID site, [docs/infrastructure §3](../infrastructure/README.md#gateway-of-a-moved-instance))
  with their own certificates. The same frontend build: the gateway's `/instance-config.js` comes
  from the `GATEWAY_CG_*` variables of the Caddy container and carries `gatewayTargetUrl`, which
  switches the web app to the gateway page.
- **Service worker**: at `/service-worker.js`, the URL the old app's worker was registered under
  (scope `/`), the gateway's site serves a small replacement worker from the Caddy image
  (`docker/caddy/gateway-service-worker.js`, `no-cache`, `text/javascript`) instead of the build's
  worker: it deletes the old app's caches, takes control and reloads the old app's pages into the
  gateway page ([docs/frontend](../frontend/README.md#service-worker-on-a-gateway)). The main site
  serves its own worker as before. Nothing in front of Caddy may cache `/service-worker.js` or the
  shell beyond what `no-cache` allows (a CDN in front of the old domain: no "cache everything" or
  edge-TTL rule for these paths).
- **Configuration** in `.env.selfhost`: `CG_ENABLE_GATEWAY`, `CG_GATEWAY_DOMAIN`,
  `CG_GATEWAY_ID_DOMAIN`, `CG_GATEWAY_SESSION_SECRET` and `CG_MAIL_LIMIT_SECRET` (shared by both
  instances for the per-address mail limits; `init.sh` generates both), optionally
  `CG_GATEWAY_TWITTER_CALLBACK_URL` and `CG_GATEWAY_WALLETCONNECT_PROJECT_ID`. Mail, chains, X keys
  are the instance's; LUKSO sign-in uses the instance's `onchain` service (`CG_ENABLE_BLOCKCHAIN`).
  `selfhost.sh up` refuses a gateway without its domains or `CG_MAIL_LIMIT_SECRET`, with the
  instance's own domains or secret, with `CG_DOMAIN` under `CG_GATEWAY_DOMAIN` (cookies scoped to
  `.<gateway domain>` — the old instance's session cookie, named like the instance's — would reach
  the instance; the gateway api refuses such a `TRANSFER_TARGET_URL` itself, too), or with
  `CG_LEGACY_CGID=true` on the instance itself (whose backend refuses it as well). A gateway under
  `CG_DOMAIN` is fine (both session cookies are host-only).
- **Isolation**: own session secret and Valkey key prefix (`gateway:`), a host-only cookie on the
  old domain; see auth-identity §12. Other host names under the old domain still receive the
  cookies browsers keep for the whole old domain: while the gateway runs, the old zone holds only
  the gateway's two names (SELFHOST.md, "Old host names"). Switched off, its `gateway:` keys stay in Valkey (the copies of the
  session generations have no TTL); SELFHOST.md has the command that removes them.

**Checking the worker replacement with a browser that has the old app** (dress rehearsal; the
e2e `gateway` flow covers it only with a stand-in for the old worker). The old app's build carries
absolute `https://app.cg/…` URLs (its `index.html` script tags, its precache list and the cached
shell `https://app.cg/index.html`), so it only works as installed from `app.cg` itself. Most faithful
therefore: a **separate browser profile** on a test machine, the real app installed from the live
`https://app.cg`, then the old domains pointed at the test VM by that machine's hosts file — with
the test VM's gateway configured for the real names for this test (`CG_GATEWAY_DOMAIN=app.cg`,
`CG_GATEWAY_ID_DOMAIN=id.app.cg`, `CG_TLS_MODE=internal`, the test CA trusted on that machine). (The
alternative, an old build served under `app.test`, needs the `production` branch rebuilt for that
origin.) Remove the hosts entries and the profile afterwards.

1. In the test profile (Chrome; once more in Firefox, Safari if available) open
   `https://app.cg/`, sign in with a test account if wanted, and install the app (address bar →
   Install). DevTools → Application → Service workers: `https://app.cg/service-worker.js`, scope
   `https://app.cg/`, *activated and is running*; Application → Cache storage:
   `workbox-precache-v2-https://app.cg/` with the old app's files. Optionally allow notifications
   (Application → Push messaging shows the subscription).
2. Close the installed app and every tab. Add `<test VM IP> app.cg id.app.cg cg.test` to the
   hosts file (the gateway runs on the test VM), and make sure the browser resolves it (restart
   the browser; Chrome may use secure DNS — turn it off in the test profile).
3. Start the installed app (not a tab). Expected, within a few seconds: it shows the old app from
   its cache first, then reloads by itself once and shows "Common Ground has moved to cg.test"
   with the sign-in form. Repeat with a tab on a deep link (`https://app.cg/c/<community>/`).
4. DevTools → Application → Service workers ("Update on reload" and "Bypass for network" **off**,
   so the browser's own update path is tested): the registration's script is still
   `https://app.cg/service-worker.js`, the running version is a new one (higher number), its
   source (click the script) starts with the replacement's header and `VERSION = 'gateway-sw-1'`.
   Console (with DevTools open during the switch, "Preserve log" on): `gateway-sw-1: activated, N
   cache(s) deleted, reloading M page(s)`. Cache storage: empty. IndexedDB/Local storage: still
   there (with the rehearsal's copy of the production data, the device key signs in silently).
   Network tab: `/service-worker.js` with `Cache-Control: no-cache`, `Content-Type:
   text/javascript`; the reloaded document came from the network ("Size" not "(ServiceWorker)").
5. Reload a few times and leave the tab open for a minute: no further automatic reloads; the
   worker version stays the same.
6. Sign in and continue: the transfer link lands on `cg.test/<path>` of the page the app was on.
7. Push (G7's script against the subscription of step 1, if one was made): the notice appears
   once with its text; a click opens the gateway page.

Failure signs: the old app stays (worker still the old version — check the Network tab for the
`/service-worker.js` response and that nothing in front of Caddy serves it from a cache); a reload
loop (the worker console shows repeated activations — the version changed between loads, or the
gateway serves a different file each time); a frozen page after the switch (a worker that waits
for its own reloads inside `activate`, see docs/frontend).

## 4. Graceful degradation of optional integrations

Every third-party integration is optional. Leaving its key(s) empty in
`.env.selfhost` disables the corresponding feature cleanly: the server derives
capability flags from which secrets are configured and ships them to the
frontend via the instance config, so unavailable features are hidden or replaced
with an honest message rather than breaking. The two backend *services* that can
be dropped at deploy time are covered separately in
[3.8](#38-optional-services-calls-and-blockchain). The `features` flags
(`email`, `twitterAuth`, `calls`) are computed in `srv/util/instanceConfig.ts`;
the Caddy-rendered `/instance-config.js` gets the equivalent `CG_FEATURE_*`
booleans from `docker-compose.selfhost.yml` (`${SMTP_HOST:+true}` etc.).
`CG_FEATURE_EMAIL` only checks that `SMTP_HOST` is non-empty, so an otherwise
invalid SMTP configuration shows the email UI while the backend has email off
(the `api` startup log says why).

| Env key(s) | Feature | Behaviour when unset |
|---|---|---|
| `SMTP_HOST` (+ `SMTP_*`, `EMAIL_FROM`; see [3.9](#39-email-smtp-and-the-mail-relay)) | email verification, one-time-code login, event & newsletter mails | password/passkey/wallet login still work; OTP login and newsletter UI hidden |
| `CAPTCHA_PROVIDER`, `ALTCHA_HMAC_KEY` / `CG_RECAPTCHA_SITE_KEY`, `GOOGLE_RECAPTCHA_SECRET_KEY` | signup captcha | fail-closed default: self-hosted ALTCHA (no external keys needed); reCAPTCHA auto-selected when its secret is set; `off` only explicit (see `docker/SELFHOST.md`) |
| `TWITTER_API_KEY`, `TWITTER_API_SECRET` (+ OAuth2 vars) | Twitter/X login and account linking | X buttons hidden |
| `CG_GIPHY_API_KEY` | GIF picker in the composer | GIF picker hidden |
| `CG_WALLETCONNECT_PROJECT_ID` | WalletConnect wallets (QR / mobile deep-link) | injected wallets (MetaMask etc.) still work |

Token staking (Spark) and bot accounts are likewise off by default and enabled
via `.env.selfhost` — see [`docs/staking`](../staking/README.md),
[`docs/BOT-API.md`](../BOT-API.md) and `docker/SELFHOST.md`.

## 5. Resource footprint & tuning

Verifiable defaults seeded by `init.sh` into `.env.selfhost`, sized for a 16 GB
machine:

- `REDIS_MAXMEMORY=1024mb` — the Valkey **state** instance
  (`--maxmemory ${REDIS_MAXMEMORY:-1024mb}`, `noeviction`): sessions, Socket.IO
  pub/sub, rate-limit windows, replay guards. A hard ceiling on purpose —
  nothing here may be evicted silently, so writes (new logins included) fail
  once it is hit. `.env.selfhost` files from before 2026-10-31 carry `1536mb`
  (then the budget of the single instance), which now applies to the state
  instance alone.
- `REDIS_CACHE_MAXMEMORY=256mb` — the Valkey **cache** instance
  (`allkeys-lru`): evicts its least recently used entries when full, so it can
  never push the state instance into out-of-memory errors. Not in older
  `.env.selfhost` files; the compose default applies.
- Host setting: `vm.overcommit_memory = 1` (sysctl) — the state instance forks
  for its background snapshots and Valkey warns at startup without it
  (`harden.sh` sets it, [3.11](#311-server-hardening)).
- `SEAWEED_VOLUME_LIMIT_MB=1024` — SeaweedFS volume chunk size.
- `MEDIASOUP_DISABLE_LIBURING=true`.
- `db` runs with `shm_size: 256m`.
- mediasoup spawns one media worker per CPU core (see
  [`docs/realtime/`](../realtime/)).

Postgres tuning lives in `docker/db/postgresql.conf` (not in `.env.selfhost`),
sized for the same 16 GB machine: `shared_buffers=1GB`,
`effective_cache_size=4GB`, `work_mem=8MB`, `maintenance_work_mem=256MB`,
`max_connections=200`, `jit=off` (full list and reasons in the file and in
[docs/infrastructure §1](../infrastructure/README.md#db-postgresql)).

**Connections.** Every backend process caps its pool with `PG_POOL_MAX`; the compose file sets it
per service, overridable in `.env.selfhost` (`PG_POOL_MAX_API`, `PG_POOL_MAX_WSAPI`,
`PG_POOL_MAX_MEMBERLIST`, `PG_POOL_MAX_JOBS`, `PG_POOL_MAX_ONCHAIN`, `PG_POOL_MAX_MEDIASOUP`,
`PG_POOL_MAX_GATEWAY_API`, `PG_POOL_MAX_GATEWAY_WSAPI`). Worst case with every pool full:

| | connections |
|---|---|
| api 20, wsapi 10, memberlist 6, job-runner 9 worker threads × 3 + 1 (its main thread's health probe, one query at a time), onchain 10, mediasoup 4 | 78 |
| gateway-api 5, gateway-wsapi 3 (when the gateway runs) | 8 |
| migrate-db (TypeORM pool, at start only) 10, a backup's `pg_dump` 1–2, admin sessions, `superuser_reserved_connections` 3 | ~20 |
| **total** | **~106 of `max_connections=200`** |

One connection of each wsapi (the typing cache), of memberlist and of mediasoup is a LISTEN connection held for good, inside its pool. The health probes ([docs/infrastructure](../infrastructure/README.md#backend-health-checks)) run inside the pools; the job-runner's main thread uses its pool for its probe alone.

The headroom covers a second api or wsapi or larger pools; raise `max_connections` (and restart
`db`) before the sum gets close to it. The reference guide
`docker/SELFHOST.md` reports the stack idling at well under 2 GB, with RAM mostly
consumed under load (calls, many users, image processing) — treat this as an
operator observation rather than a code-verified figure.

### Memory limits

Every service in `docker-compose.selfhost.yml` has a `mem_limit`
(`${CG_MEM_LIMIT_<SERVICE>:-default}`, the service name upper-cased with `_`
for `-`), so a leak or a runaway request in one service hits its own limit —
the kernel's OOM killer ends that container and Docker restarts it — instead
of starving the database or the whole server. Measured on the disposable e2e
instance (2026-11-02, F7 acceptance; the full browser suite with sign-ups,
chat, images, a call, articles; blockchain off): `docker stats` maxima, cache
excluded, sampled every 2 s, and the cgroup `memory.peak` (cache included):

| Service | Default limit | e2e max (`docker stats`) | e2e `memory.peak` | Reasoning |
|---|---|---|---|---|
| `db` | `4g` | 147 MiB | 223 MiB | `shared_buffers=1GB` + up to 200 connections × `work_mem`; the page cache of the data files counts against the limit, so it also bounds how much of the database stays cached — raise it with `shared_buffers` |
| `redis` | `2g` | 5 MiB | 10 MiB | `REDIS_MAXMEMORY` 1024 MB plus the snapshot fork (copy-on-write, up to about the data size again): a full instance must refuse writes (`noeviction`), not be killed. Keep it ≥ 2 × `REDIS_MAXMEMORY` |
| `redis-cache` | `512m` | 4 MiB | 10 MiB | `REDIS_CACHE_MAXMEMORY` 256 MB, no snapshots |
| `seaweed` | `1g` | 79 MiB | 79 MiB | needle index in memory grows with the number of files; `GOMEMLIMIT=870MiB` (about 85%) |
| `caddy` | `512m` | 274 MiB | 299 MiB | includes the cache of the served frontend files (~100 MB with source maps); `GOMEMLIMIT=435MiB` (about 85%) |
| `api` | `2g` | 294 MiB | 322 MiB | the NSFW model (onnxruntime), Chrome for social preview images (`htmlToImage`) next to Node |
| `wsapi` | `1536m` | 58 MiB | 92 MiB | grows with open websockets |
| `memberlist` | `4g` | 30 MiB | 31 MiB | keeps every community's member and role sets in memory — grows with the data, which the e2e instance does not have; 4 GB gives it a 2 GiB heap (Node's own cap from a 4 GB limit on; without any limit it had 4 GiB on a large host) |
| `job-runner` | `4g` | 194 MiB | 213 MiB | one V8 isolate per worker thread, each capped at `JOB_WORKER_MAX_OLD_SPACE_MB` (default 384 MB, `srv/jobs.ts`): at most nine run at once (four permanent, five scheduled, each at most once), 9 × 384 MB = 3.4 GB, plus the main thread (orchestration and the health probe) — the sum fits the limit. Without the cap every worker sized its heap like the main thread (half the container limit) |
| `onchain` | `1536m` | — | — | not in the e2e run (blockchain off); ethers providers per chain, the NSFW model for avatar ingests |
| `mediasoup` | `2g` | 63 MiB | 84 MiB | one worker process per core; grows with participants (one two-person call here) |
| `migrate-db` | `2g` | — | — | one-shot; migrations that rewrite large tables run in it (1 GiB heap) |
| `mail` | `256m` | — | — | maddy; not in the e2e run (Mailpit there) |
| `gateway-api` | `1g` | 96 MiB | 101 MiB | half of `api`'s: only the gateway's sign-in routes — no NSFW model (`IMAGE_MODERATION_ENABLED=false`), no social preview images. Profile `gateway`; measured in a separate e2e run with the gateway (2026-11-06, the full suite plus the gateway flow and `e2e/checks/gateway.sh`) |
| `gateway-wsapi` | `512m` | 79 MiB | 84 MiB | a third of `wsapi`'s: no logged-in sockets, only the short-lived ones that watch a CG ID popup's result. Profile `gateway`; same run as `gateway-api` |
| `cg-builder` | `6g` | — | — | the frontend build: ~2.65 GiB `memory.peak` (Vite 8, see [3.2](#32-dockerselfhostselfhostsh--build-and-operate)), `--max-old-space-size=4096` |

All containers together peaked at about 1.2 GB (sum of the `docker stats`
maxima). The limits are ceilings, not reservations: their sum (about 23 GB
for the long-running services, 1.5 GB more with the gateway) exceeds a 16 GB server on purpose — services do not peak
together, and each limit only has to keep one service from taking the
machine. What bounds the defaults from below is Node: a Node process sizes
its heap from its cgroup limit — measured with this image (Node 26): 1 GB →
536 MiB heap, 2 GB → 1072 MiB, 4 GB and more → 2144 MiB; without a limit it
was 4192 MiB on the 30 GB dev VM. A Node service therefore gets about half its
limit as heap, at least 512 MiB. The e2e data is tiny; the dress rehearsal
with production data (roadmap P5) must check `selfhost.sh stats` against
these limits — `memberlist`, `api` and `db` first — and raise the defaults
where real data needs it. TODO(verify): usage with production data.

The Go services (`caddy`, `seaweed`) get `GOMEMLIMIT` at about 85% of their
limit, so their garbage collector works harder before the kernel's limit is
reached (`CG_GOMEMLIMIT_CADDY` / `CG_GOMEMLIMIT_SEAWEED`; `selfhost.sh`
derives them from an overridden `CG_MEM_LIMIT_CADDY` / `CG_MEM_LIMIT_SEAWEED`).
`selfhost.sh up` warns when `CG_MEM_LIMIT_REDIS` is less than twice
`REDIS_MAXMEMORY`.

**Database connections of the health checks** (for the connection
arithmetic of `max_connections`): each backend process's probe runs one
`SELECT 1` at a time on that process's own pool, so it needs no connection of
its own while the pool has an idle one, and at most one more otherwise
(node-postgres closes idle connections after 10 s). The job-runner's main
thread opens no other connections: its pool exists only for the probe and
holds at most **one** connection — whatever pool size a setting for the
job-runner (e.g. a `PG_POOL_MAX_JOBS`) gives the workers, the main thread
counts as one.

### Log rotation

Every self-host service logs through Docker's `json-file` driver with
`max-size=${CG_LOG_MAX_SIZE:-20m}`, `max-file=${CG_LOG_MAX_FILE:-5}` and
`compress=true` (the `x-logging` anchor in `docker-compose.selfhost.yml`):
at most about 100 MB of logs per container, the rotated files gzipped.
`docker inspect -f '{{json .HostConfig.LogConfig}}' cg-selfhost-api-1` shows
the setting of a running container; it applies to containers (re)created
after the change, which `selfhost.sh up` does. The host's own logs (journald)
are bounded by `harden.sh` ([3.11](#311-server-hardening)).

## 6. Legacy CI/CD pipelines (Azure DevOps / Ansible / Swarm)

> These pipelines target the hosted app.cg / staging.app.cg infrastructure and
> are **legacy**: they predate the self-host profile and the planned move to
> GitHub Actions (§7). They are documented here for completeness and for
> operators of the hosted deployment. Self-hosters do not use them.

The hosted deployment uses **Azure DevOps Pipelines** (YAML). Two pipelines
exist under `pipelines/`, plus a shared clean-up template.

### Staging — `pipelines/build-and-deploy-beta.yml`

- **Trigger:** push to the `staging` branch. **Pool:** `ubuntu-20`.
- Installs Docker 20.10.14, Node 24.x, the `packageManager`-pinned Yarn (via corepack), plus
  build tooling; pulls a private `.yarnrc` as a secure file. **That secure file
  replaces the repository's `.yarnrc.yml`**, so the pipeline re-appends
  `enableScripts: false` and `npmMinimalAgeGate: 1w` after copying it — without
  that, CI builds would run without the supply-chain controls the repo
  configures (see docs/infrastructure §2).
- Copies `srv/` into `docker/backend/dist/`, generates a build ID (pipeline
  variable `CG_BUILD_ID`, embedded by the frontend build and passed to the
  backend image build as `--build-arg`), and builds the prod frontend with `PUBLIC_URL="https://staging.app.cg"` (which
  now only keeps the default social-preview meta absolute — asset URLs are
  root-relative on every path).
- Builds and pushes the **backend** and **nginx** images to the
  `commonground staging registry` (tags `beta`, `$(Build.BuildNumber)`); nginx
  is built with `SERVER_NAME=staging.app.cg`, `CGID_SERVER_NAME=id.staging.app.cg`.
- **Deploys via Ansible** over SSH (`ansiblemanager03`) into **Docker Swarm**:
  the main stack (`docker_swarm_deploy_beta.yml`) and mediasoup
  (`deploy_docker_mediasoup.yml`) against their respective inventories. The
  playbooks live in a separate infrastructure repository.

### Production — `pipelines/build-production.yml`

- **Trigger:** push to the `production` branch. Steps mirror staging with:
  `PUBLIC_URL="https://app.cg"`; images pushed to the
  `commonground prod registry` (tags `0.1`, `latest`, `$(Build.BuildNumber)`);
  nginx build args `SERVER_NAME=app.cg`, `CGID_SERVER_NAME=id.app.cg`.
- **No Ansible step** — production is a **build-only** pipeline; the Swarm
  rollout is performed separately/manually.

### Clean-up — `pipelines/sub-templates/clean-up.yml`

Shared template that removes the build work directory; runs
`condition: always()`.

### Required infra-repo cutover: one Redis instead of three

> **Action item for the hosted (Swarm) deployment — must land before or with the
> next image rollout.** As of 2026-10-31 no further Swarm rollouts are planned:
> the hosted instance moves to a single self-host server instead
> (`docs/todo/ROADMAP_cg-box.md`), so this only applies if the Swarm stack is ever
> rolled out again.

As of 2026-08-01 the backend connects to a **single** Redis instance: every
client in `srv/redis/index.ts` resolves `process.env.REDIS_URL ||
'redis://redis:6379'`. The Swarm stack files in the separate infrastructure
repository still publish three services (`redis-sessions`, `redis-socketio`,
`redis-data`), which the new image no longer looks for. Rolling out the image
against an unchanged stack makes **every** backend process fail to reach Redis
at once — sessions, rate limiting, captcha, bot presence and the Socket.IO
adapter all go down together.

Either fix works:

1. **Merge the three Swarm Redis services into one named `redis`** (same
   `--requirepass`/`--save ""`/no-eviction config; size `maxmemory` to roughly
   the sum of the three), or
2. **Set `REDIS_URL` on every backend service** (`api`, `wsapi`, `job-runner`,
   `onchain`) to whichever instance is kept, and retire the other two.

Option 1 matched both compose files in this repo at the time. Either way the
cutover logs everyone out once. Since 2026-10-31 the image additionally expects
a cache instance (`REDIS_CACHE_URL`, default `redis://redis-cache:6379`; it may
point at the same server as `REDIS_URL`) — without it, URL previews are just
built uncached and the backend logs a connection error every 30 s.

### Hosted deployment topology

- Images are built in CI and pushed to per-environment registries.
- Runtime orchestration is **Docker Swarm** (implied by the playbook names);
  mediasoup runs on dedicated hosts separate from the main stack.
- TLS is terminated at the edge (Cloudflare), not inside the nginx container —
  the opposite of the self-host profile, where Caddy terminates TLS in-stack.

For the security posture of these pipelines (no automated tests, no approval
gate, `printenv` step, etc.) see the private infrastructure security notes;
they are out of scope for this public document.
